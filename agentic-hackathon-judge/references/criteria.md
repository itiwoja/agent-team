# 審査基準と採点ルーブリック

公式は3軸を示しているが配点は非公開。本スキルでは**各5点・同じ重み・計15点**で仮採点する。これは公式採点ではない。

## 公式の3軸

**課題の新規性と解決策の有効性**
多くの人が抱えながらも、いまだ解決策が与えられていない課題を発見できているか。提案されたソリューションがその課題の核心に効果的に対処し、実質的な価値をもたらしているか。

**自律性・エージェントらしさ**
単純な自動化を超え、状況を判断しながら自律的に行動するエージェントとして設計されているか。その自律性が適切に管理・制御されており、可観測性やセキュリティへの配慮を持った、信頼できる動作をするか。

**実装品質と拡張性**
アイデアをどれだけ高い品質で実現できているか。必要なツールを適切に活用し、拡張性・運用性・費用対効果を考慮した、実用に耐えるソリューションを構築できているか。

## 各軸の一言要約（審査員の頭の中）

| 軸 | 一言 |
| --- | --- |
| 課題 | 多くの人が実際に困っているのに、今の方法では解決できていない理由を説明できるか |
| 自律 | 自分で考えて動くが、許可された範囲から出られず、何をしたか全部説明できるか |
| 実装 | 「これデモ用に一本道で作っただけでは？」と思われないか |

## 点数の意味（共通）

| 点 | 意味 |
| --- | --- |
| 5 | 軸の中核が具体的で非常に強い。証拠（動作・計測・比較）がある |
| 4 | 強いが、比較検証か一部の証拠が足りない |
| 3 | 成立するが、差別化か設計に課題がある |
| 2 | 重要な前提や設計が不足している |
| 1 | 評価材料がほぼない |

## 軸1：課題の新規性と解決策の有効性

| 確認項目 | 5点の状態 | 2点以下の状態 |
| --- | --- | --- |
| 誰が困っているか | 具体的な人・場面・頻度が言える | 「みんな」「業務効率化」 |
| なぜ未解決か | 既存手段（人手・既存ツール・固定ルール）で解けない理由がある | 既存SaaSやスクリプトで足りる |
| 解決の核心性 | 困りごとの根本に効いている | 周辺の便利機能にとどまる |
| 効果の証拠 | 改善前後を同じ条件で比較・計測している | 効果が主張のみ |

**よくある減点**
- ChatGPT／Gemini に直接聞けば済む（エージェントにする必然性がない）
- 課題が作り手の想像だけで、利用者の声・観察がない
- 成果指標がない、または測っていない

## 軸2：自律性・エージェントらしさ

| 確認項目 | 5点の状態 | 2点以下の状態 |
| --- | --- | --- |
| 自律ループ | 観測 → 判断 → 作用 → **再観測して選び直す**が回る | 1回呼んで終わり、固定手順の自動化 |
| 判断の必然性 | 状況によって次の行動が変わり、固定ルールでは書けない | if文で書ける分岐をLLMにやらせている |
| 権限境界 | 実行してよい範囲・ツール・データが明示され、コードで強制されている | プロンプトで「〜しないで」と頼むだけ |
| 停止・人の確認 | 危険・不確実なときに止まり、人に確認する条件がある | 止まる条件がない |
| 可観測性 | 判断理由・実行した操作・結果がログ／タイムラインで追える | 何をしたか後から分からない |
| セキュリティ | 秘密情報・プロンプトインジェクション・外部作用への配慮がある | 考慮なし |
| 検証 | 合否をAIの主観ではなく明示ルール・独立した判定で確かめる | AIの自己申告で「完了」 |

**よくある減点**
- 「自律的に動きます」だけで、制御・説明可能性がない（今回は自律だけでは点にならない）
- チャット欄に入力して返答が返るだけ（チャットボット）
- 失敗時の挙動がデモに出てこない

## 軸3：実装品質と拡張性

| 確認項目 | 5点の状態 | 2点以下の状態 |
| --- | --- | --- |
| 動作 | デプロイURLで審査員が自力で主要機能を一通り触れる | 動画でしか見られない／動かない |
| 頑健性 | 入力や状況を変えても動く。エラー処理・リトライ・タイムアウトがある | 決め打ち入力でしか動かない（一本道） |
| ツールの使い方 | 各技術に採用理由があり、ないと成立しない | 技術名の羅列、使っただけ |
| LLM以外の強い技術 | 物理エンジン・GIS・DAW・シミュレーター等の専用エンジンで検証している | 全部LLMに任せている |
| 運用性 | ログ・監視・設定・デプロイ手順が整っている | 手元でしか再現できない |
| 拡張性 | 対象やデータを増やす道筋が構成上ある | ハードコード |
| 費用対効果 | 1回あたりのコスト・応答時間を把握している | 不明 |
| コード品質 | 責務分離、READMEとの一致、テストや評価スクリプト | READMEとコードが食い違う |

**よくある減点**
- 技術スタックを全部使おうとして浅くなる（必要性のない技術は加点しない）
- 構成図が実装と一致しない
- 審査用アカウントが動かない、サンプルデータがない

## Tier基準

| Tier | 条件 | 意味 |
| --- | --- | --- |
| A | 12点以上、かつ全軸3点以上 | ファイナリスト圏を狙える。弱点の比較検証に集中 |
| B | 9〜11点、または12点以上でも2点以下の軸がある | 有望だが弱点の解消が先 |
| C | 8点以下 | 現状の構成では3軸を同時に示しにくい。テーマか範囲の見直しを推奨 |

## 加点しないもの

- 文書量、技術・機能の個数、AR／物理などの要素の個数
- 「予定」「想定」「今後」の機能
- 実測していない効果の数値
- スポンサーサービスの利用そのもの（利用の有無は審査に影響しない）
