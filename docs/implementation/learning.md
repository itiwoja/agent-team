# 成長機構の実装手順（ステップ3〜6・9）
- プロジェクト：Makase ／ 手順書の版：v1.3（2026-10-26） ／ 設計の版：v1.8

> **3行で**
> 1. 日程調整の履歴から、条件付きの実行IRを生成・検証・自動採用する。
> 2. 本体の土台→常駐→カレンダー接続→画面→効果測定の順で既存手順に組み込む。
> 3. 各L節は対応ステップの一部であり、後回しの任意作業ではない。

## 前提（始める条件）
- [実装順](README.md#v18-の追加範囲)の対応ステップまで完了していること。L4はL3、L5はL4と5.6、L6はL5、L9はL6とステップ8を前提にする。
- 正本は[機能仕様](../design/04_functional_spec/learning.md)、[DB](../design/08_database/learning.md)、[API](../design/09_api/learning.md)、[画面](../design/06_learning.md)、[統合技術仕様](../design/11_learning.md)。数値や状態を変更するときは設計へ戻す。
- L3・L4は偽の時計・カレンダー・ScriptedLlmで検証する。L5の実接続は試験用カレンダーと既存OAuth、L9の実モデル評価は価格が判明した接続先と予算、ラズパイ5 16GBを用意する。

## 手順
### L3 本体の土台
ステップ3.10の後に実施する。
1. TBL-064〜068を既存SQLiteへ追加するマイグレーションを作る。適用番号は既存連番の次とし、TBL-035へ `learning.enabled=true, revision=1` を追加する。設定のlimitsはサーバー側に置き、公開PATCHで変更できるのはenabledだけにする。
2. DB正本のJSON検査・FK・状態enum・部分UNIQUE・CAS・不変版をrepoで実装する。candidate時の検証参照はNULL、採用時は同一programのfinal検証参照・旧版superseded・監査を同一トランザクションで更新する。
3. 閉じたIR schemaと先行参照のDAG検査を作る。32ノード上限、登録済みread／transform／guard／hole／proposeのみ許可する。任意コード・動的ツール・未知キー・丸暗記定数を拒否し、汚染は伝播する。
4. `normalizeWindow`・`intersectFreeBusy`・`enumerateSlots`・`selectSlot`を版付き純粋演算にする。半開区間とUTC計算、IANAでの表示を分ける。scopeは入力schema・接続identity・カレンダー集合・選択規則版まで厳密照合する。
5. 採用用oracleと固定反例集合を候補生成から独立して用意する。FR-119の必須10カテゴリを各10件以上含め、実装対象自身の出力を期待値にしない。

確かめ：空DBへの適用と既存DBからの更新、FK検査、採用競合のロールバック、schema拒否、DSTと区間境界、scope誤一致を試験する。

### L4 常駐と学習
ステップ4.10の後に実施する。コネクタはreadとIntent提案の契約を持つ偽物にし、実際の書き込みはL5で接続する。
1. 型付き受付 `schedule.propose.v1` をFR-117に合わせて検査する。期間・長さ・件数・タイムゾーンを制限し、選択規則は明示入力のみ。通常経路とIR経路の分岐は型付き入力確定後に置く。
2. 本体のツール窓口で観測を採取する。tool／owner／hypothesisの出所を本体で付け、秘密・会議本文・実カレンダーIDを学習用入力から除く。再現不能なredactionや記録失敗はeligible=falseと理由を残し、通常実行を継続する。
3. 既存5分tickに候補生成を接続する。同scopeの適格成功履歴5件以上、期間2種類・空き時間パターン2種類を確認する。同digest・同根拠の重複、同scope非終端候補の競合を抑止する。
4. 静的検査→元履歴の再生→100件以上の反例→生成後の異なる5依頼のシャドー→採用直前照合を実装する。すべて合格した場合だけ自動採用する。検証側には書込クライアントを渡さず、シャドーは通常経路の観測を共有する。ScriptedLlmでも5段階を省略せず試す。
5. RegistryとExecutorをつなぐ。runごとに版を固定し、毎回read、各ノード後に契約検査、次ノード前に停止・依存版・期限を確認する。初回・scope不一致は通常経路、契約違反はinvalidatedにし未送信時だけ通常経路へ戻す。
6. Hole Resolverを既存裏タスク枠で動かす。最大4穴・各2試行、read-only道具、tool／ownerの根拠とfreshnessを検査する。待機中はcheckpointを保存してexecutor枠を解放し、完了通知で同じrunを再開する。再委譲や実行中IRの書換えはしない。
7. deny・権限不足はblocked、好み不明はneeds_owner、timeout・429は既存再試行、送信結果不明はunknown_outcomeへ分ける。これらをガードmissと混同してLLMへ迂回させない。
8. 30秒リース・10秒更新・epoch付き更新、ノード／hole／checkpointの同一トランザクション、再起動時の古いreadと子孫の無効化を実装する。完了済み副作用の子孫は再実行しない。
9. 学習上限・全体／自動予算・接続先規約を既存の窓口で適用する。生成60秒、検証10秒ごとのcheckpointとyield、run同時1・検証同時1でユーザー処理を優先する。価格不明・予算／容量不足では新規学習を待機させる。穴の費用はtask、候補生成は学習費へ計上する。
10. 5分tickと実行直前に期限・根拠欠落・依存変更を確認する。保持削除の順序と参照解除はDB正本に従い、進行中run・未確定Intentを保持する。全体OFFは版状態を変えず、版停止はdisabled。再有効化で失効版を復活させない。

確かめ：偽時計で期限・予算・容量・保持を進め、候補生成から採用、穴待機中の枠解放、停止競合、再起動、偽の根拠拒否までを試す。FR-119の各ゲートを1つずつ失敗させ、activeにならないことを確かめる。

### L5 外部接続とAPI
ステップ5.8の後、5.6のカレンダー移植を使って実施する。
1. `calendar.freeBusy.v1`と`calendar.createEvent.v1`を既存コネクタへ結ぶ。IRのproposeも既存Kernel・承認・Intentを通す。Executorやresolverから直接書く経路を作らない。
2. 承認後／送信直前のpreflightで空きを再取得する。30秒を超えた観測は取り直し、変更時はIntent破棄→再計算→内容が変われば再承認する。
3. `runId + nodeId`のeffect keyとIntent IDを一意に関連づけ、送信予定を先に永続化する。送信後応答欠落・リース失効ではunknown_outcomeとし、再送や通常経路での作り直しを止める。コネクタで結果照合できなければ人へ戻す。
4. API-158〜162を既存の持ち主認証・CSRF・冪等性へ接続する。API-160のexpectedUpdatedAt、API-162のexpectedRevisionをCASで検査し、監査と同時更新する。bindingsや観測の生値を返さず、LLMのツールに登録しない。
5. API-122へlearningRunIdを追加し、採用・失効・停止・run更新は既存SSEの再取得通知でつなぐ。チャットへの報告は既存send_to_owner経由にする。
6. UC-073〜076を通す。実接続は試験カレンダーで既存承認後に1件登録し、候補計算成功と登録結果を別に記録する。採用用の再生・反例・シャドーは実カレンダーへ書かない。

確かめ：承認待ち中の予定変更、送信後応答欠落と再起動、停止と送信の競合、CAS競合・同key異body・未認証／非所有者・不正cursorを試す。実外部サービス間の原子性を保証したと扱わない。

### L6 画面
ステップ6.7の後に実施する。
1. SCR-034を既存設定、SCR-035をtask詳細のlearningRunIdから開く。検証段階の件数・範囲・期限・停止理由・版・穴・費用をAPIから表示する。
2. 全体OFFと版停止を分け、送信済み取り消しとは表示しない。競合時は最新状態を取得して再確認し、404・空・通信失敗・taskId不一致を扱う。
3. unknown_outcomeは再送していないことを示す。候補計算だけで登録完了とせず、入力解釈・報告にLLMを使う場合はサービス全体を「AI呼び出しゼロ」と表示しない。
4. 320px幅・キーボード・色以外の状態表示・aria-liveを確認する。学習費と通常実行費を分けて表示する。

確かめ：UC-076の停止と通常AI機能の継続、実行詳細から版詳細への遷移、エラー・競合・保持例外の表示を画面で確認する。

### L9 評価とリリース
ステップ9.12の後に実施し、以下が終わるまでリリース完了にしない。
1. 採用試験や候補生成に使わない固定holdoutを100件以上用意する。同じ観測を通常経路とIR経路へ渡し、seed・モデル版・operator版・suite版を保存する。外部書き込みは行わず、出力契約と独立oracleで成功を判定する。
2. NFR-098を測る。成功率低下は2ポイント以内、型付き入力確定後のLLM呼出総数は50%以上削減。未知・失敗・途中停止も母数に入れ、通常経路0回の削減率はN/Aにする。入口解析・報告・穴・学習の回数と費用を別に記録する。
3. 学習費＋実行費と通常経路の同件数費用を比較し、損益分岐件数を測る。未償却なら安くなったと断定しない。NFR-099の費用・件数・同時数・容量上限を段2の継続運用でも確かめる。
4. ラズパイ5 16GBでNFR-100を測る。32ノード以下の純粋計算p95 200ms以内（外部API・LLM・DB待機を除外）、再起動後60秒以内の未完了run再判定、結果不明の自動再送0件を確認する。
5. NFR-101の30日保持・active期限・根拠欠落時失効・100%の説明記録・秘密保存0件を検査する。保持削除は偽時計、バックアップ復旧は実DBで確認し、依存版・アカウント・期限再確認と未確定送信の照合待ちを通す。
6. 導入手順書へ既定ON、日次費用上限、停止方法、保持例外、結果不明時の確認、復旧手順、実測結果を追加する。機能成功・推論削減・費用・性能を別々に合否判定する。

確かめ：評価結果に母数・未知件数・版・計測環境を残し、NFR-098〜101の未達を隠さない。実モデルや実機未実施の項目は未完了と記録する。

## 実装で決めること
- マイグレーション番号、repo・IR演算のファイル分割、採用suiteとholdoutの固定seed・版管理、計測結果の保存先を実装時に決める。
- コネクタの照合可能範囲は実APIで確認する。照合不能時は人へ戻す既定契約に従う。
