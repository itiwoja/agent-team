## 手順
### 9.1 隔離の試験を全体の構成で全部通す（段 1。WSL2）
11 §11 の隔離の行を 1 行 1 試験にする。構成は `docker compose up -d` で起こした本番と同じもの（本体・`tailscale`・`box-manager`・`docker-socket-proxy`・`egress` ＋ box-manager が起こす VM）。**試験は必ず本番の Compose でやる**（ステップ 1 の `compose.vm.yaml` や開発用の上書きでは通ったことにしない）。VM は `curl` で API-101 を叩くか、タスクを 1 つ頼んで起こしておく（画面に起こすボタンはない）。

| # | 試験（11 §11 隔離の行） | 叩く場所 → 叩くもの | 期待 |
|---|---|---|---|
| I-1 | VM から本体に届かない | `docker exec -u agent shell curl -m 5 http://makase:8080/` と `:8081`。`box-browser` からも | 名前が引けない・つながらない |
| I-2 | VM から box-manager の口に届かない | `shell` と `box-browser` から `box-manager:7000`・box-manager の IP | つながらない（box ネットワークの box-manager は管理の口を呼ぶ側。`/internal/v1/*` は本体のトークンなしで使えないことも） |
| I-3 | VM から `192.168.x`・`100.64.x`・`::1`・IPv4 を入れた IPv6（`::ffff:192.168.x.x`）に届かない | 両コンテナから egress 経由（`curl --proxy`）と直（`curl --noproxy`）。ホストの LAN の別の機械と tailnet の別の端末のアドレスを実際に使う | egress は断る。直はつながらない |
| I-4 | ホストのブリッジのアドレスに届かない（`isolated` モードか任意の規則を入れた構成で） | `shell` と `box-browser` から box ネットワークのゲートウェイのアドレス（`docker network inspect`）の開いているポート（ホストの sshd など）へ | つながらない。`isolated` も規則もない構成では**届くのが正**。結果を README の「ホストへの入り」に書いたとおりか照らす（確かめ方の分岐は「実装で決めること」） |
| I-5 | DNS rebinding で抜けない | 引くたびに答えが変わる名前（自分で立てた DNS か `rebind` を返す公開サービス）を `box-browser` で開く・`box-shell` で `curl` | 1 つでもグローバルでないアドレスを含む答えは断られ、つなぎ先は確かめたアドレスに固定される（egress のログに「断った」が残る） |
| I-6 | `web_fetch` からも同じアドレスに届かない（D-164） | 本体のメインに `http://192.168.x.x/`・`http://[::1]/`・リダイレクトで内側へ向ける自前のページを `web_fetch` させる（または本体の道具を直に呼ぶ試験口） | どれも断られる。リダイレクト先も再判定される |
| I-7 | インターネットから 443 番に届かない（D-241） | 9.1 の外側の機械で `curl -m 10 -sv https://makase.<tailnet>.ts.net/` | つながらない・拒否される |
| I-8 | インターネットから 8443 番の `/hooks/` だけが届く | 外側で `curl -si -X POST https://makase.<tailnet>.ts.net:8443/hooks/<hookId> -d '{}'`（署名なし） | 401。404 ではない |
| I-9 | Funnel から :8080 の口（`/api/*`・`/`）に届かない | 外側で `https://...:8443/` と `/api/health` | どちらも 404（200 や HTML が返れば失敗） |
| I-10 | 8443 番の `/hooks/<hookId>` がパスのまま :8081 に届く（D-305） | I-8 の 401 に加え、本体のログの受けた経路が `/hooks/<hookId>`。署名つきで 202 | 401→202。パスの頭が落ちていない |
| I-11 | 成果物の HTML のスクリプトが動かない（D-243） | `<script>` で `fetch('/api/health')` を書いた HTML を成果物にし、ダウンロードの応答ヘッダーと `?preview=1` のプレビューを見る | `Content-Disposition: attachment`・`nosniff`・`CSP: sandbox`。プレビューで fetch が動かない |
| I-12 | `box-shell` から `box-browser` の X・CDP・VNC・box-agent・プロフィールのボリュームに届かない（D-326） | `docker exec -u agent shell`：box-agent・VNC の口へ `curl`・`nc`、`/tmp/.X11-unix` を探す、`/home/browser` を見る、`ps` で相手のプロセスが見えないこと | すべて失敗（ステップ 1 の #6 の再確認） |
| I-13 | `box-shell` の通信が許可リスト外（LAN を含む）に出られない | `shell` から `curl --proxy egress` で許可リスト外の公開サイト・LAN のアドレス | 断られ、egress のログに送り元 `box-shell` が出る |
| I-14 | Chromium から `shell:8000` だけが egress を通さず開け、`shell` 以外のホストは egress を通る | `shell` で簡易サーバーを :8000 に立て、`box-browser` の Chromium で `shell:8000` と公開サイトを開く。egress のログを見る | `shell:8000` は開けてログに出ない。`shell` 以外のホストは egress を通り、ログに出る |
| I-15 | `box-browser` から `box-shell` の shell-agent にトークンなしで何もできない | `docker exec browser` から `shell` の管理の口へ `curl`（`healthz` を含め）、古い世代のトークンで | すべて断られる |
| I-16 | `~/work/<taskId>` に置いたリンクが成果物にも差分にも写らない（D-306） | `shell` の `~/work/<taskId>` に `ln -s /home/agent/.cache/x`・`ln -s /etc/passwd`・`ln -s ../../..` を作り、成果物の取り出し（API-118）と差分を見る | リンク・絶対パス・`..` は捨てられ、中身が写らない |

手順：
1. 試験ごとに `evals/isolation/` に 1 つのスクリプト（または手順の 1 節）を書く。スクリプトは「叩く・期待と照らす・OK か NG を 1 行で出す」だけにし、`docker exec` で実行する。結果は日付・ホスト・Docker の版・Compose のコミットとともに表にして残す
2. I-4 は `isolated` モードの Docker の版かどうかで構成が変わる。9.2 の「ホストへの入り」の方針を先に決めてから試す
3. I-7〜I-10 は Funnel が要るので、受け口を 1 つ作って（画面の SCR-026）から行う。終わったら受け口を消し、8443 番が閉じるまで確かめる（ステップ 5 の 5.4 の 6）
4. 1 つでも NG なら、直す前にその NG を再現する手順を `evals/isolation/` に残してから直す。直したら 9.1 を最初から通す

確かめ：I-1〜I-16 がすべて OK で、記録の表が残っている。ステップ 1・5 で個別に通した試験と矛盾がない。

### 9.3 マルチアーキのイメージをビルドして置く（段 2・段 3 の前）
README の約束（`TARGETARCH` 依存は arm64 の分岐も書く・Compose とイメージ名は arch で分けない）を守っているかをここで一括して確かめる。
1. 本体・box-manager・egress・box-browser・box-shell・（tailscale は公式のイメージを digest で固定）のイメージを、`docker buildx build --platform linux/amd64,linux/arm64` で 1 つのタグ（マニフェストのリスト）にして置き場へ push する。ベースイメージの digest は**マニフェストのリストの digest**で固定する（`check-image-digests.mjs` が通ること）
2. どこでビルドするか：GitHub Actions に `release.yml` を足す。おすすめは arm64 を **arm64 の runner**（`ubuntu-24.04-arm`）でネイティブにビルドし、amd64 と合わせてマニフェストを作る。QEMU での arm64 は Chromium のイメージで遅い・落ちることがあるので避ける（ためして決める）。アクションは SHA で固定し、権限は `packages: write` だけをそのジョブに
3. 置き場：GHCR（`ghcr.io/<owner>/makase-*`）が第一候補（リポジトリと同じ GitHub・OSS は無料・匿名で pull できる）。タグはリリースの版と `latest`。`compose.yaml` の `image:` はこれを指す（`build:` は `compose.dev.yaml` に残す）
4. ビルドの前に `better-sqlite3` が arm64 の prebuilt で入ること、`chromium`（Debian）が arm64 にあること、`TARGETARCH` を使う Dockerfile の行に arm64 の分岐があること、`pnpm-workspace.yaml` の `onlyBuiltDependencies` が arm64 でビルドできるものだけであることを確かめる
5. amd64・arm64それぞれイメージなし環境でComposeとVM2イメージを明示pullし、公開手順だけでVM起動まで確認。更新後は新しい世代の解決後digestも記録する（IMP-011）
6. 家の機能のイメージ：Home Assistant は公式のマルチアーキのイメージを**マニフェストのリストの digest** で固定する（自前ではビルドしない）。判断モデル（`decision`）と 4B 級の生成モデルを動かすサービス（llama.cpp か Ollama など。ステップ 8 で決めたもの）も arm64 のイメージがあるものを digest で固定し、重みはイメージに焼かずボリュームに置く（ライセンスの確かめは 9.9）
7. SBOM と署名は今回の範囲外（要るなら後で）

確かめ：1 つのタグで amd64 と arm64 の両方が pull でき、CI の `check-image-digests` が緑。段 2 の VM で README の `pull` から起動する。

### 9.8 キットのイメージを作って手渡す（FR-109・SCR-033・API-157・NFR-094）
[運用契約のキットの作り方と手渡し](../design/11_operations.md)の段階どおりに作る。
1. **イメージの作成**：Raspberry Pi OS 64bit に Docker・Compose 一式（9.3 の公開リリースの digest で固定）・Home Assistant・判断モデルを入れ、起動時に `docker compose up -d` が走るようにして、イメージに固める（`kit/build-image.sh`）。秘密（`BOX_MANAGER_TOKEN`・`ENCRYPTION_KEY`・`VAPID_*`）はイメージに焼かず、**初回の起動で 1 台ごとに作る**（同じイメージの全台で鍵が同じにならないように）
2. **書き込み**：ラズパイ 5 の 16GB と 8GB に、内蔵ストレージと USB の SSD（512GB 以上。保管庫 `makase-vault`）を書き込む。起動して `docker compose up -d` が通り、SCR-033 が開くこと
3. **QR の台紙**：Tailscale の招待（1 人ぶん・期限つき）と SCR-033 の QR を 1 枚に印刷する（`kit/card/`）
4. **手で通す**：自分で 1 回、箱を開けるところから①電源と LAN（または Wi-Fi をスマホから設定）→②Tailscale の招待→③パスキーの登録→④「ChatGPT でサインイン」（デバイスコードをスマホで承認。API キーの道も 1 回）→⑤最初のお願い、まで通す。途中でスマホを閉じても続きから始まる（API-157 の状態）。QR の期限切れ・キーが通らない・Tailscale につながらないときの言葉（FR-109 の例外）を 1 つずつ起こして見る
5. **第三者テスト（NFR-094）**：非エンジニア 3 人に、箱と台紙だけを渡して説明なしで始めてもらう。**電源を入れてから最初のお願いが通るまで**をストップウォッチで測る。口頭の補足をしない・詰まりの数え方は 9.5 と同じ。3 人中 2 人以上が 15 分以内なら通り。詰まった箇所は台紙・SCR-033 の文・写真つきの手順書に戻す
6. 手渡しの線引き（サポートする・しない）は運用契約の表のとおりに伝える（R-111）

確かめ：キットのイメージから 2 台（8GB・16GB）が起き、自分の通しで ①〜⑤ が通った。非エンジニア 3 人中 2 人以上が 15 分以内。

### 9.9 段 3：ラズパイ 5 で家の機能を測る（NFR-092・096・ADR-083）
9.8 のキット 2 台（8GB・16GB）で測る。数字は見積もりなので、実測で 05 の NFR-092 の表を直す（R-77・R-112）。
1. **同居（NFR-092）**：本体＋VM（Chromium の仕事中）＋Home Assistant＋判断モデル＋4B 級の生成モデルを同時に動かし、`free -m`・`docker stats`・`OOMKilled`・swap を 1 時間記録する。16GB は全部同時に動くこと。8GB は VM を起こしている間、本体が 4B の生成モデルを止める（排他。D-380）ことを見る
2. **`classify` の速さ（NFR-096）**：ラズパイ 5 で `classify` を 1,000 回呼び、p95 が 1 秒以内。LLM に回った件数も数える
3. **判断モデルの候補（R-109）**：候補（Laya の多言語版を先に、次に Von・Rizzo Flow）を、日本語のレシートの費目で精度・速さ・メモリ・**ライセンス**（AGPL と両立し、キットに入れて配れるか）を確かめ、既定を決める
4. **4B 級の生成モデル（NFR-093・096）**：`summary` と短い文章の役割での速さ・メモリ・道具の呼び出しを測る。`main`・`worker`・`computer` に選べないこと
5. ステップ 8 の家計簿の試し（NFR-097、レシート 50 枚）を、キットの既定の構成（画像はクラウド・費目は判断モデル）でもう一度通す
6. 実測を 05 の NFR-092・096 の横に「実測（ラズパイ 5・8GB／16GB・日付）」で書き足す。8GB で同居できないものがあれば NFR-092 の表と 11 §12 の R-112 を直す

確かめ：NFR-092 の表が実測で直っている。`classify` の p95 が 1 秒以内。判断モデルの既定が決まり、ライセンスが確かめてある。

### 9.10 ChatGPT の無料アカウントで確かめる（R-113・D-390）
無料と Plus のアカウントで、キット（ラズパイ 5）から「ChatGPT でサインイン」を通す（FR-116）。ステップ 3 の終わりに一度試していれば、その記録に足す。
1. 無料のアカウントで、デバイスコードのサインインが通り枠が使えるか。使えなければ 403 で理由が出て、API キーの道に案内されること
2. 枠の大きさ：チャットの頼みを何件で 429 になるか（無料・Plus）。429 とストリームの途中の `response.failed` で、ほかの支払いに切り替えずターン・タスクが止まり知らせが来ること（D-388）
3. 画像の入力と computer use が呼べるか（D-390）。呼べても、利用規約で許されるか確かめるまでは能力に `vision`・`computer_use` を足さない
4. 利用規約：常駐・自動のきっかけでの使い方が許されるか。分かるまで `llm.chatgpt_allow_auto = false` の既定を変えない（D-389）
5. 結果を 11 §12 の R-113 の横と ADR-084 の「確かめること」に書く。キットの初回設定（SCR-033）の文と、9.8 の手渡しの説明を結果に合わせる

確かめ：無料・Plus それぞれで、サインイン・429 の止まり方・画像・computer use・規約の結果が記録されている。

## 設計に戻すこと
