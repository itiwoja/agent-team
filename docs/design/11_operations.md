# 運用契約：停止・移行・VMイメージ（P1）
- 版数：v1.7（2026-10-26）／親：[技術仕様](11_tech_spec.md)

> **3行で**
> 動的VMはComposeだけでは止まらない。
> コピーは書き手を止めてボリュームが非使用になってから行う。
> Compose外の2イメージも公開リリースのdigestで明示取得する。

## 🧭 判断してほしいこと
なし。IMP-010・011の承認済み改善案に沿う。

## 全体の順序
受付/自動起動停止 → 対象VM停止/削除 → ボリューム非使用確認 → コピー/削除または新digestで起動。

## 要点
- 新規基盤は追加しない。Docker labelと既存の停止APIを使う。
- 具体的なイメージdigestはリリース成果物として固定し、架空値を書かない。

## 停止とコピー（IMP-010）
1. 本体の新規受付・タイマー・VM自動起動を止める。本体を停止し再起動させない。managerが利用可能な間にAPI-102で対象世代を止め、続いてmanagerを停止して自動再作成を防ぐ。
2. managerが作る全VMには `io.makase.managed=vm`・`io.makase.installation=<導入固有ID>`・`io.makase.generation=<boxId>` を付ける。導入IDはホストの運用設定で固定し、世代とは別。停止済みを含む当該導入のコンテナだけを列挙し、停止・削除する。managerが落ちた場合もこのlabelから回収する。無関係なコンテナは触らない。
3. 稼働中コマンド・Chromiumが終了し、対象の動的コンテナが0、対象ボリュームを利用する他コンテナも0であることをDocker inspectで確認する。不明/利用中ならコピーしない。Composeサービスもdownして本体DBの書き手をなくす。
4. 通常停止はボリュームを残してここで終了。移行は停止済み `makase-data`・`makase-browser-profile`・`makase-vm-home` と、`makase-vm-snapshots/.operations/` を同じ停止時点の組として読み取り専用でコピーする。`.operations/`（未ACK結果・broken印・ACK済み墓標）は控え本体を引き継がない場合も必須。未完了の復元が参照する控え本体も必須で、それ以外の控え本体だけ省略できる。移行先の起動前にコピー元との記録・ファイルの一致を確認し、欠落/不一致なら起動せず人へ復旧要求する。空の記録を未受付のnoneと解釈して再送してはならない。
   Tailscale状態は旧ホストを再起動しない前提で移すか、新規認証し直すかを明記し同時利用しない。`.env` の暗号鍵は安全な別経路で移す。
5. 完全削除は対象データを消す明示確認後だけ。動的VMを片付けた後、当該導入の名前付きボリュームを列挙して削除する。`compose down -v` だけで全データが消えると説明しない。

移行の受入：復元/消去のdoneまたはfailedが未ACKの状態、およびDB結果確定後ACK応答消失の状態で移行する。新ホストが同じoperationIdの結果/墓標を照合してACKだけを完了し、破壊的操作を再実行しないこと、brokenが維持されることを確認する。`.operations/` を意図的に欠落させた移行は起動前検査で停止し、POST/消去DELETEが0回であることも確認する。

## 初回・更新のイメージ（IMP-011）
- リリースはComposeサービス群とmanagerが使う `BOX_BROWSER_IMAGE`・`BOX_SHELL_IMAGE` の不変digest対応を一組で公開する。2変数はAPI入力にせずmanagerの固定設定だけで使用する。
- 初回は `docker compose pull` に加え、公開された2値で `docker pull "$BOX_BROWSER_IMAGE"`・`docker pull "$BOX_SHELL_IMAGE"` を実行し、両方の取得成功/対象CPUの解決を確認してからupする。build運用も同じ参照へタグ/IDを揃え、存在確認する。
- 更新は新リリースの一組を先に取得し、取得失敗なら旧版を維持。上の停止契約で旧世代を片付け、Composeとmanagerの2参照を同じリリースへ切り替え、次の新世代が指定digestを使うことをAPI-109/111とDocker inspectで確認する。
- amd64・arm64のイメージなしホストで公開手順だけから起動することを受入条件にする。manifest digestと各CPUの解決後digestを記録し、Compose pull成功だけで合格としない。

## 閉域での置き方（v1.6・D-340〜342・358）
`network.mode = closed`（家の中だけで動かす）で置くときの用意と手順。インターネットに出さない。
| 用意するもの | 中身 |
|---|---|
| 入口 | Headscale（自前の調整サーバー。`tailscale serve` が同じヘッダーを付けるので `OWNER_LOGIN` で確かめる）か、社内 LAN の直結（社内 CA の TLS 証明書。本体のパスキー）。Tailscale の SaaS と Funnel は使わない |
| 社内 CA | 本体の TLS 証明書を発行する。持ち主の端末に社内 CA を入れる |
| 知らせ | Web Push は切る。画面の中の通知（SSE）と、任意で社内に置いた ntfy（`closed` の許可リストに書く） |
| 推論サーバー | 社内の Ollama・vLLM など。全役割を `openai_compatible`（`base_url`）にし、`network.allow_hosts` に明示すると外向きが 0 になる（D-356）。ラズパイには置かない（D-357。v1.7：D-380 で、ラズパイ 5 の 4B 級は `summary` と短い文章の役割に限って選べる）。最低の条件は NFR-093 |
| 社内システム | VM で届かせる先は `network.internal_hosts` に書く（ブラウザとターミナルで別。既定は `confirm`）。社内の Git はターミナルの `git`（D-367） |
| webhook | 社内の GitLab・GitHub Enterprise Server から LAN の中で受ける |
| 使えないもの | Google カレンダー・GitHub.com・Web 検索（D-356）。イメージは、閉域に入れる前に取得して持ち込む（上の IMP-011 のdigestで確かめる） |

パスキーの最初の登録：本体を起こしたあと、ホストで `docker compose exec makase makase owner-enroll` を実行する。出た 1 回限りの URL を、社内 LAN の持ち主の端末で開いて登録する。使った URL は無効になる。ログインは 12 時間のセッション Cookie。
`closed` に切り替えた直後は、台帳（SCR-027）で拒否の件数を見て、許可リストの足りない先を確かめる。

## キットの作り方と手渡し（v1.7・D-372）
家の人に渡すセットアップ済みのラズパイ。最初は知り合い数人に手渡す。
| 段階 | 手順 |
|---|---|
| イメージの作成 | Raspberry Pi OS 64bit に Docker・Compose 一式・Home Assistant・判断モデルを入れ、イメージにする。公開リリースの digest で固定したイメージを使う（IMP-011） |
| 書き込み | ラズパイ 5（8GB 以上。推奨 16GB）の内蔵ストレージとUSB の SSD（512GB 以上）にイメージを書き込む。起動して `docker compose up -d` が通ることを確かめる |
| QR の印刷 | Tailscale の招待と、画面の「はじめての設定」（SCR-033）の QR を台紙に印刷して箱に入れる。招待は 1 人ぶん・期限つき |
| 手渡しのとき | ①電源と LAN（または Wi-Fi をスマホから設定）→②スマホに Tailscale を入れ、QR で招待を受ける→③画面の QR からパスキーを登録→④ChatGPT でサインイン（短いコードをスマホで承認する。API キーは要らない：D-387）、または API キーを貼る（写真つきの手順書を渡す：D-384）→⑤最初のお願い。目標は 15 分以内（NFR-094） |

## ChatGPT のサインインと枠（v1.7・D-385〜390・R-113）
手順の「API キーを貼る」の代わりに「ChatGPT でサインイン」でもよい（D-387）。
| やること | 手順 |
|---|---|
| つなぐ | 画面の「はじめての設定」（SCR-033）または モデル（SCR-029）で「ChatGPT でサインイン」→ 出た短いコードを、スマホのブラウザで確認の URL に入れて承認する。トークンの共有も承認する |
| 枠を決める | 利用者が `chatgpt.com/settings/usage` で、このアプリの週の上限を割合で決められる。Plus は 5 時間ごとの上限を全アプリで分け合う。上限に当たると仕事は止まり、画面で知らせる（ほかの支払いには切り替えない：D-388） |
| 切る | モデル画面の「ChatGPT の接続を切る」（本体のトークンを消す）。利用者が `chatgpt.com/settings/usage` 側から切ることもできる（切られても本体に通知は来ない。次の呼び出しで「接続が切れた」と出る） |
| つなぎ直す | 切れた表示から、もう一度「ChatGPT でサインイン」。モデルの一覧は取り直され、割り当ては残る |
| 自動のきっかけ | 既定では ChatGPT の枠を使わない（`llm.chatgpt_allow_auto = false`：D-389）。ルーチン・webhook・予約は家の中のモデルか API キーで動く |
| `closed` のとき | `auth.openai.com` と `api.openai.com` を `network.allow_hosts` に入れる |

## 保管庫の控え（任意・NFR-095）
`makase-vault` の控えは、毎週、別のディスクか NAS へ取る（任意）。保管庫はゴミ箱（30 日）と前の版（30 日）で守られるが、SSD の故障には効かない。控えを取る先と日を手順書に書く。ゴミ箱を空にするのは人だけ。

## Home Assistant の更新（v1.7）
Home Assistant のイメージは、本体のイメージとは別に更新する。更新の前に Home Assistant の設定を書き出す（HA の標準の控え）。更新のあと、本体の `home` の接続と機器の一覧（`home_devices`）が戻っていることを SCR-032 で確かめる。長期トークンは本体が持つので、HA を作り直したら新しいトークンを貼る。

## 監査ログの先頭のハッシュを外に控える（D-350・R-103）
- 毎日 0 時に、監査ログの末尾のハッシュが `audit_anchors` に残る。その日のうちに、本体の外（別のホスト・紙・社内の文書管理など、root を取られても書き換えられない場所）に控える。API-151 の `GET /api/audit/anchors` で書き出せる。
- 検査（`POST /api/audit/verify`）は、鎖の途切れと、控えたハッシュとの食い違いを見る。ホストの root を取られた場合に守れるのは、外に控えた先頭より後だけ。控えていない期間は守れない。
- 規則（`policy.json`）の書き出しも、版のハッシュ（`policy_sha256`）と一緒に控えておくと、あとから変えられていないか確かめられる。

## 台帳の書き出し（D-344）
SCR-027 の CSV（API-148 `GET /api/egress.csv`）で、外に出た通信（送り元・宛先ホスト・目的・バイト数・許可/拒否・LLM のトークン数。中身は残さない）を出す。行は 90 日、日ごとの集計（`egress_daily`）は無期限。監査や情報システム部への報告のために、月に 1 回の書き出しを勧める。移行のときは `makase-data` に入っているので、上の移行の手順で一緒に移る。
