# ADR-033：仕事を本番に出す前に、リハーサル（模擬の世界での障害試験）を通す
- 状態：承認 ／ 日付：2026-10-02 ／ 決定者：プロダクトオーナー（[D-37](../decisions.md#d-37)）
- 影響する ID：FR-026, FR-042〜045, BR-61〜63, REQ-059〜061, ADR-015, ADR-018, ADR-027, [15](../15_hackathon.md)

## 状況
v0.5 でエージェントは自分で設定するようになった（ADR-026）。権限を広げる変更は人に戻す（ADR-027）が、**許した範囲の中で起きる失敗**（単位の取り違え、値上がり、タイムアウト後の扱い）は、正常な場合を一度走らせる試し実行（FR-026）では見つからない。ハッカソンでは、デモが「一本道に見えないこと」と「自律性が管理されていることを説明できること」も求められる。

## 決定
- 試し実行を拡張した **リハーサル** を作る。Gemini が固定の障害カタログから仕事に合わせた状況を作り、状態を持つ模擬の世界（`sim-world`、MCP サーバー）に対して本番と同じ経路で実行し、決定論的なオラクルで合否を出す。
- すり抜けた失敗に対しては、`classify()` が `narrow` と判定する変更（ガードの追加など。BR-61）だけを提案し、適用後に同じシードで再試験する。
- リハーサルの走行は `sim-world` にしか書き込めない（BR-63）。

## 理由
- 合否をオラクル、実行の許可を Kernel が決めるので、LLM の判断は「状況を考える」「締める案を出す」に限られる（ADR-018 と同じ考え方）。
- 本番と同じ経路を通すので、リハーサルで確かめた結果が本番とずれない（ADR-015 の理由を引き継ぐ）。
- 模擬の世界が MCP サーバーなので、実のコネクタと同じスキーマで差し替えられ、題材を増やしても仕組みは変わらない。

## 代替案
| 案 | 良い点 | 悪い点 | 不採用の理由 |
|---|---|---|---|
| 試し実行（正常な場合）のまま | 追加の実装がない | 起きてほしくない日を試せない | 状況に書いた課題を解けない |
| LLM に結果を採点させる（LLM-as-judge） | オラクルを書かなくてよい | 合否が再現しない。モデルの判断で許可が決まる | 決定論的な統制という製品の筋に反する |
| 実のサービスのサンドボックス環境で試す | 本物に近い | 用意できるサービスが限られ、障害を自由に注入できない | 再現性と障害の網羅で劣る |

## 影響
- 新しいテーブル：`rehearsal_runs`・`rehearsal_scenarios`・`job_guards`、スキーマ `sim`。
- リハーサルの費用（Gemini）が加わる。1回 $3 までとし（D-104 で $0.5 から $1.0 に、D-106 で $3 に見直し）、日次予算に含める（BR-62）。
- 承認待ちの Intent は、リハーサルでは「承認した場合」と「却下した場合」の両方に分岐して走らせるので、1件の状況から走行が増える。
