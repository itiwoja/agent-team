# ADR-057：画面の操作は子の文脈で行い、親には短い報告だけ返す
- 状態：置き換え済み（→ ADR-059。Q-124 は決着。2026-10-24） ／ 日付：2026-10-24 ／ 決定者：Claude判断（提案）
- 影響する ID：FR-075, FR-084, FR-088, R-82, ADR-050

## 状況
コンピューターユースは 1 歩ごとにスクショを Claude に返す。今の設計では、依頼を進める 1 つの会話（文脈）の中でスクショを回し、画像は直近 3 枚だけ残す（D-161）。それでも、

- スクショの画像と古いスクショの代わりの文が、依頼の本筋（聞き取った条件・手順書・ターミナルの結果）と同じ文脈に積もる
- 1 歩ごとに、本筋の長い文脈ごと Claude に送り直すので、歩数とともに入力トークンが増える（R-82）

参考資料（[GrokBot のスライド](../../../参考資料/index.md) の 9・10 枚目）では、メインのエージェントは画面を操作せず、画面操作の担当に「何をしてほしいか」だけを渡し、担当からは短い報告だけが戻る。作業の記録は担当の側で止まり、失敗・中断した担当は続きから動かせる。

## 決定（案）
- 依頼を進めるエージェント（親の文脈）は、ブラウザの操作を道具 `use_browser(goal, hints)` として頼む。`goal` は「何ができたら終わりか」を 1〜3 文で書く
- 本体は、同じタスク・同じエージェント・同じ VM のまま、別の会話（子の文脈）を立てて computer use のループを回す。子が持つのは `goal`・`hints`・エージェントの指示の要約・ブラウザの道具（computer use・`open_url`・`read_page`・`confirm_action`・`request_takeover`）だけ
- 子が終わったら、親には「できたこと・できなかったこと・取ってきた値・最後の URL」だけを文で返す（スクショは返さない。要るときは親が `use_browser` でもう一度頼む）
- 子の歩みも `task_steps`（TBL-038）に `parent_step` つきで記録する。再起動・失敗・交代のあとは、子の歩みの記録から続きを動かす（FR-084 の表に「子の文脈」の行を足す）
- こわい操作の判定（FR-076）・確認（FR-077）・交代（FR-078）は今のまま。子が出した操作も同じ Kernel の関数を通る
- 子の費用は親のタスクの上限（FR-013）に含める。子 1 回の上限は操作 100 回（`browser.max_actions_per_goal`）

## 代替案
| 案 | 良い点 | 悪い点 | 不採用の理由 |
|---|---|---|---|
| 今のまま 1 つの文脈（D-161 で画像を 3 枚に絞る） | 作りが単純。親が画面を直接見て決められる | 歩数が多い仕事ほど文脈と費用が膨らむ | R-82 の対策として弱い |
| 画面操作を別のエージェント（別の人格）にする | 役割がはっきりする | 「1 件の依頼はエージェント 1 人」（ADR-050）とぶつかる。プロフィールの持ち主があいまいになる | 子は同じエージェントの別の文脈にとどめる |
| 子の文脈を使うかを Claude に任せる（道具を両方出す） | 短い操作は親がそのまま済ませられる | 2 通りの道ができ、試験と再開の場合分けが倍になる | 最初は `use_browser` に一本化し、実測（MS-1）で外れたら見直す |

## 影響
- ADR-050 の「1 件 1 人」は変わらない。子は同じエージェント・同じ VM・同じプロフィールで、別人ではない
- FR-075 の 1 歩の流れは子の文脈の中の流れになる。親の道具から computer use を外し、`use_browser` を足す（FR-088）
- `task_steps` に `parent_step`（TEXT、親の歩みのキー）を足す
- 決めるのは MS-1 の実測（1 タスクの入力トークン・費用）を見てから。採用なら MS-3 で入れる（12_implementation_order.md は v1.0 で削除）
