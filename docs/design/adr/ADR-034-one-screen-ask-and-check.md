# ADR-034：毎日使う画面を「頼む・チェック」の1枚にし、承認も同じチェックにする
- 状態：承認 ／ 日付：2026-10-02 ／ 決定者：プロダクトオーナー（[D-42〜45](../decisions.md#d-42)）
- 影響する ID：SCR-019（新規）, SCR-002・003・006・014（日常の入口から外す）, SCR-007, ADR-005, ADR-026, ADR-027, ADR-031, NFR-041, A-22, R-20

## 状況
v0.6 までの画面は「管制盤」で、ホーム・タスク・承認・エージェント・その他の5つの下部タブと、19 の画面があった。ユーザーは用事のたびに「どの画面に行くか」「誰に頼むか」を考える必要がある。v0.5 で「名前を付けて頼むだけ」にした作り方（ADR-026）と比べて、使う側の画面だけが重いままだった。プロダクトオーナーは「ユーザーはしてほしいことを頼むだけ、こなしたものはチェックするだけ」にしたいと考えている。

## 決定
- 毎日使う画面を SCR-019「頼む・チェック」（`/`）の1枚にする。中身は「見てほしいもの」「やっていること」「頼む欄」の3段だけ（D-42）。
- 承認も報告と同じ ○ で行う。確認シートはやめ、押してから5秒の取り消し猶予を置き、猶予が過ぎてから表示していた `intentHash` で承認を送る。宛先は行の2行目に大きく出す。却下と [以後も許可] は行を開いた中に置く（D-43）。
- エージェント一覧はホームの入口から外し、メニューの奥に置く。エージェントは各行に添える担当の名前として毎回見せる（D-44）。
- エージェントからの聞き返しは「チェックだけ」の例外として、選択肢のボタンで答える。自由に書くのは選択肢にならないときだけ（D-45）。

## 理由
- 見る場所が1つで、操作が ○ と選択肢だけなら、ユーザーが考えるのは「チェックするか」だけになる。
- 承認の確認シートは「押す → 読む → 確定」の2段で、日に何度もあると読まずに確定する癖がつく。押す前に読める行（何を・宛先・「送る」）と、押した後に取り消せる猶予のほうが、操作は1回で誤操作も戻せる。
- 承認と表示の結びつき（ADR-005）は、ユーザーに8文字のハッシュを見せることではなく、表示した `intentHash` を送ることで守られる。猶予が過ぎてから送るので、サーバー側の仕組みは変わらない。
- v0.5 の「エージェントは名前のある担当者として見せる（目標の裏に隠さない）」は、各行に担当の名前を出すことで満たす。一覧を日常の入口に置く必要はない。

## 代替案
| 案 | 良い点 | 悪い点 | 不採用の理由 |
|---|---|---|---|
| 今の5タブの管制盤のまま | 設計済み | 入口が多く、毎回どこへ行くかを考える | 「頼むだけ・チェックするだけ」にならない |
| 承認だけスワイプや長押しにする | 誤タップを防ぎやすい | 操作が2種類に増え、見ただけでは分からない | 操作を1つに絞る方針に反する。取り消しの猶予で誤タップは戻せる |
| エージェントのチャット（SCR-018）を入口にする | v0.5 の設計のまま | エージェントが増えると、どのチャットを開くかを考える | 担当を選ぶ手間が残る |

## 影響
- SCR-002・003・006・014 は日常の入口から外れる。SCR-014・017・018 と SCR-007 の中身は、メニューの奥と行を開いた中で引き続き使う。
- 下部タブ（BottomTabBar）をやめ、AppHeader のメニューにする。
- デザイン方針の原則5「承認・却下・キャンセルは確認シート」を改める：承認は取り消しの猶予、却下は開いた中で理由を任意に、キャンセル・Kill Switch は従来どおり確認シート。
- 「チェック済み」を記録する置き場（列か表か）と、依頼を受ける API を T-1 の設計作業で決める。
- R-20（[以後も許可] の誤タップ）は、[以後も許可] を一覧から外し開いた中だけに置くことでさらに下がる。
