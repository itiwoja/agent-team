# ADR-031：MCP の書き込みは自動で再試行せず、結果不明は `unknown_outcome`、検証は `none` / `readback` にする
- 状態：承認 ／ 日付：2026-10-01 ／ 決定者：ユーザー（15：プロダクトオーナーが承認）
- 影響する ID：BR-59, FR-012, API-070, `connector_tools.verify`

## 状況
Intent のライフサイクルは PR 専用で、`succeeded` は PR の検証まで、自動の再試行（最大3回）が前提になっている。MCP の書き込みには読み戻しの標準がなく、送信後の再試行は二重送信になりうる。

## 決定
- **実行の失敗**：MCP の書き込みは自動で再試行しない（送信前の失敗＝名前解決・接続拒否・TLS だけ最大3回）。送信後のタイムアウト・接続断・5xx は `unknown_outcome` にし、ユーザーが「実行済み / 失敗 / もう一度実行」を確定する。
- **検証**：ツールごとに `none`（既定）/ `readback`（フェーズ1）。`none` の Intent は `executed` で終わる。

## 理由
二重送信を避ける。読み戻しの標準がないため、検証はツールごとの設定にする。

## 代替案（これまで）
| 案 | 良い点 | 悪い点 | 不採用の理由 |
|---|---|---|---|
| GitHub と同じ最大3回の自動再試行 | — | 二重送信のおそれ | 上記の理由 |
| `verified` まで進む前提 | — | MCP には読み戻しの標準がない | 同上 |

## 影響
- [もう一度実行] は同じ引数で新しい Intent を作り、二重のおそれをカードに書いて承認を求める（ルールがあっても `auto` にしない）。
- `succeeded` の意味を「外部作用がすべて実行された（検証できるものは検証済み）」に広げる。
- Gateway での実行の手順（ロック・`tool_hash` の確認・タイムアウト60秒）は 04、状態遷移は 10。
