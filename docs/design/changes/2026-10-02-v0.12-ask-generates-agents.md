# 変更：頼むとエージェントが生成される（v0.11 → v0.12、2026-10-02）
> **3行で**：入口を「仕事はエージェントに任せて」の1文と入力欄だけの SCR-020 にした。頼むと「エージェント生成中…」になり、設定プランナーが合う担当を使い回すか新しく作る。1体で足りない依頼は、並列・まとめ・順番の形で独立した複数のエージェントに分ける ／ 名前を付けて1体ずつ作る手順（ADR-026）をなくし、頼むだけで任せたいというプロダクトオーナーの要望に合わせたため（[ADR-036](../adr/ADR-036-ask-generates-formation.md)・[ADR-037](../adr/ADR-037-entrance-one-sentence.md)、[D-63〜68](../decisions.md#d-63)） ／ いちばん大きい影響は、チェックの画面（SCR-019）が `/check` に移って頼む欄がなくなったことと、エージェントの間を結果が流れるようになったこと（汚染は受け渡しで引き継ぐ BR-71、まとめ役は書き込まない BR-72）。

## 🧭 判断してほしいこと
- **Q-109**：審査員が最初に見る画面。D-56（入口の直後にリハーサルの結果）と D-66（常に入口）がぶつかる。おすすめは「ゲストのワークスペースを作った最初の1回だけ結果の行を開き、2回目からは入口」（[15](../15_hackathon.md)）。
- 仮に置いた値（実機・計測で決め直す）：A-97 編成を見せる時間3秒、A-98 生成の打ち切り30秒、A-99 担当は5体・順番は4段まで、A-100 まとめ役は全員が終わるか30分で始める、A-101 まとめ役は書き込みを外した `briefer` で動かす。
- 形を選ぶのは設定プランナー（LLM）で、Kernel は形の正しさではなく「上限・まとめ役に書き込みがない・新しいエージェントの数」だけを検査する。分け方の良し悪しは使って確かめる（分け過ぎるとエージェントが増える）。

## 影響範囲（ID でたどったもの）
- ADR-026（名前を付けて頼む）：日常の作り方は ADR-036 に置き換え。FR-034（名前だけで作る）はメニューの奥のエージェント一覧に残す。
- ADR-034：承認の ○ と5秒の取り消し・行の種類・メニューはそのまま。入口と頼む欄だけ ADR-037 で置き換え。
- 汚染（ADR-024、BR-38）：受け渡しで引き継ぐ（BR-71）。BR-39（汚染で MCP の書き込みの判定を変えない）と O-03 は変えない。
- フェーズ2の委任（REQ-032）：別物のまま。編成は依頼の時点で決め、実行中に担当は増えない（BR-73）。

## 変えていないもの
- Kernel の `decide()`・`classify()`・ガード・ルール（v0.11）。担当ごとの書き込みは従来どおり判定する。
- 1ワークスペース20体・1エージェント10個の仕事の上限（A-81）。
- 05・07〜10 への反映（`asks`・`ask_members` の表、API-072〜074、`tasks.ask_id`、生成のシーケンス図、NFR-054 の生成の目標）は、ハッカソンの提出後にまとめて行う。実装は 04 FR-061・062 を正とする。
