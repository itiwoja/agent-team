## C-1. 全部承認する人には、確認が効かないのでは

**答えの骨子**
- その通りで、計測でも確かめている。「人が全部承認」の枝は、どの設定でも ¥234,000 前後の損害が出た（ルールなしで ¥234,000＝統制なしと同額）。確認は中身を見ないと効かない。
- だから答えは「確認を増やす」ではなく「確認を減らしても塞がっていることを、任せる前に試して示す」。「以後も許可」のルールで確認を32回から5回に減らすと ¥156,000 すり抜けた。安全チェックが出した単価 ¥1,170 以下のガードを当てると、確認17回で ¥0。確認が減れば一件ずつ読まれやすくなる、と考えている（未検証）。
- 確認の画面には「なぜ止めたか」（ガードの名前と値）を出す。中身を見ずに通すのを減らすため。
- 限界：確認の疲れそのものは測っていない（未検証）。

**根拠**
- [統制ありの計測](measurements/governed-20261006-gemini.md)の「読み方（要点）」の表：確認32回 → 5回（すり抜け 7/35・¥156,000）→ 権限を絞ったあと17回（0/35・¥0）。
- 同ファイル「確認は中身を見ないと効かない」の項と、「締めたあとに当てた変更」（`items[].unit_price` に 1170 以下のガード）。
- 同ファイルの「まとめ」の表：人が全部承認した枝は ¥234,000（ルールなし・「以後も許可」）、締めたあとも ¥234,000（11/35）。

## C-2. F-06（しなかった失敗）は止められないのでは

## C-4. 中核はどれか（カレンダー・GitHub・パックまで広げて、ぼやけていないか）

**答えの骨子**
- 中核は3つ：Kernel（書く前の判定。純粋関数、LLM なし）、決定論の判定（オラクル。合否）、安全チェック（権限を絞る提案・通った記録・止めた発注を次の試験に）。書き込みの出口は gateway だけ。
- Gemini が担うのは、エージェントの推論・編成の生成・悪い日を作ること・自分の言葉の悪い日の解釈。合否・損害額・権限を絞る提案は Gemini が決めない。
- カレンダー・GitHub・パックは、同じ統制に乗せた任せ先の例。書き込みは毎回 ○、権限は最小で、統制を弱めていない。審査していただきたいのは中核の3つで、残りは「同じ統制に別の仕事を乗せられる」ことの例。

**根拠**
- [README](../../README.md)「中核のコードはここ」「中核と、その上に乗せた任せ先」と、「もう少し詳しく」の最後の項（Gemini が担う範囲）。
- コード：[`packages/kernel/src/decide.ts`](../../packages/kernel/src/decide.ts)、[`packages/oracles/src/oracles.ts`](../../packages/oracles/src/oracles.ts)、[`packages/rehearsal`](../../packages/rehearsal/src/)。
- 決定：[D-113](../design/decisions.md#d-113)（カレンダーは scope が `calendar.app.created`・`calendar.freebusy` だけ、復号は gateway だけ、書き込みは全部 ○）、[D-119](../design/decisions.md#d-119)（GitHub App の鍵は gateway だけ、`main` は既定で保護、書き込み2ツールは両方 ○）、[D-116](../design/decisions.md#d-116)（パックの担当は権限を広げない）。
- 依存の境界：`pnpm lint:deps` で runner が DB・Gemini・gateway に届かないことを CI が検査する（[ci.yml](../../.github/workflows/ci.yml)）。

## C-5. ADK を使わない理由

**答えの骨子**
- 判定を LLM の外に置く設計（ADR-001）が先にあり、Harness と Kernel を自前で持っている。ADK はこの役割と重なり、置き換えると「判定が LLM の外にある」ことの検証をやり直すことになる。
- Google Cloud は「なくては成り立たない所」にだけ使う方針：Cloud Run は境界ごとに別サービス・別サービスアカウント、Gemini は API キーなしで IAM から呼ぶ、Cloud SQL は状態の正本。
- 「ADK の上に同じものが載るか」は試していない（未検証）。ツール呼び出しの前後に Kernel の判定を挟む形は載せられるはず、までしか言わない。

**根拠**

## C-9. 「似た依頼」をどう判定するのか

**答えの骨子**
- 類似度の計算やベクトル検索はしていない。依頼のたびに Gemini（設定プランナー）が、いまある担当の一覧（名前・役割・型・スキル・付与・仕事の例文）を読み、「すでにある担当で足りるなら、必ず使い回す」という指示のもとで担当の id を選ぶ。新しく作るのは、合う担当がいない・その担当の仕事が10個ある・依頼に「新しい担当で」とあるときだけ。
- 似ているかの判定は Gemini が一覧から選ぶ。Kernel の `validateFormation` は、一覧にある・使える・上限内だけを検査する（本当に似ているかは検査しない）。外れたら理由を添えて1回だけ作り直す。
- 使い回しの誤りは安全側に倒れる：使い回す担当の権限は広げない（足りなければ「権限は広げていません」と印を残し、書き込みは確認に回る）。似ていない担当を選んでも、権限が増えることはない。
- 「@担当名」で名指しすれば、その担当に固定できる。パックの作業場から頼めば、そのパックの担当を優先する。
- 限界：判定の精度は測っていない（未検証）。似ていない担当を選ぶことはありうる。「同じ依頼なら必ず同じ担当」とは言わず、「ふつうは同じ担当。選ぶのは Gemini」と答える。
- 分かっている制限：使い回しで引き継いだルールは、新しい仕事の安全チェックを通すまで効かない（締切後に、同じ担当の前の仕事の安全チェックの結果を引き継ぐか、自動で始めるかを決める。プロダクトオーナーの判断待ち）。担当の仕事が10件で上限（`kernel/formation.ts` の `JOB_LIMIT`・`policy.ts` の `jobs.max(10)`）に当たると、同じ種類の依頼でも新しい担当が作られ、積み上がったルールは引き継がれない。済んだ仕事も数えるため。締切後に、済んだ仕事を数えない方式を検討する。

**根拠**
- [`apps/app/src/asks/planner.ts`](../../apps/app/src/asks/planner.ts)：担当の決め方の指示（184–185行）、一覧に渡す項目（`jobHints`：45・265–266行）、担当の指定（287行）、パックの担当を優先する節（242–252行）、違反の説明文（`VIOLATION_TEXT`：307–326行）、作り直しは1回だけ（`PLANNER_MAX_CALLS`：515行）。

- 決定：[D-63](../design/decisions.md#d-63)、[D-85](../design/decisions.md#d-85)、[D-86](../design/decisions.md#d-86)、[ADR-036](../design/adr/ADR-036-ask-generates-formation.md)。

## C-10. 「使うほど良くなる」を何で測るのか

**答えの骨子**
- ここでの「使うほど良くなる」は学習ではない。同じ担当を使い回すことで、「以後も許可」のルール・安全チェックで権限を絞った設定・付与・作業場の控え・スキルが担当に引き継がれ、次の似た依頼で、その依頼で安全チェックを通したあとに確認が減ること。引き継がれたルールや権限を絞った設定は、その依頼で安全チェックを通すと効く。安全チェックの結果そのもの（本番で止めた発注を入れた試験を含む）と承認した宛先（○ を押した宛先）は仕事ごとで、使い回しても依頼ごとに新しい仕事になるので引き継がれない。新しい仕事を自動で安全チェックする経路はなく、ルールがあっても安全チェックの結果がなければ確認に回る（`certificate_missing`）。モデルの再学習や指示文の自動の書き換えはしていない。
- 指標は**人に確認を求めた回数**と**すり抜けた損害（円）**の2つを、同じ悪い日・同じシードで並べて見る。片方だけ下げるのは簡単（全部通せば確認は0になる）なので、両方で見る。
- 実測（本物の Gemini、各35走行）：ルールなし 32回・¥0 → 「以後も許可」5回・¥156,000 → 単価のガードを当てて 17回・¥0。これは**安全チェックの中で、ルールを足し権限を絞った場合に測った数字（同じ仕事）**で、**使い回しの効果そのものは測っていない**。確認が減っても塞がっていることを、再試験で示せる。
- 何が引き継がれたかは画面で開ける：担当のルール一覧、適用したガード、監査ログの番号。依頼のページの段には「いつもの担当 · 前の依頼 N件でも働きました」、ライブラリのカードには「使い回し N回 · 以後も許可にした N回 · 権限を絞った N回 · スキル N件」が出る。安全チェックの記録（ポリシー・ツール・試験のハッシュとモデル名）は、その仕事のものとして開ける。
- 測っていないもの：使い回しの効果そのもの、利用者が何日も使った推移（未検証）、使い回しの判定の精度（C-9。未検証）、確認の疲れ（C-1。未検証）。この計測は安全チェックの中のもので、本番の利用の推移ではない。

**根拠**
- [統制ありの計測](measurements/governed-20261006-gemini.md)の「読み方（要点）」の表（確認32回 → 5回 → 17回、損害 ¥0 → ¥156,000 → ¥0）。
- コード：[`packages/kernel/src/remember.ts`](../../packages/kernel/src/remember.ts)・[`rules.ts`](../../packages/kernel/src/rules.ts)（1担当のルールは20個まで：`RULES_MAX_PER_AGENT`）、[`packages/rehearsal/src/tighten.ts`](../../packages/rehearsal/src/tighten.ts)、[`certificate.ts`](../../packages/rehearsal/src/certificate.ts)（`expiryReasons`）、[`packages/kernel/src/decide.ts`](../../packages/kernel/src/decide.ts) の `certificate_missing`（202行）。
- 本ファイルの C-1（全部承認する人）。

## C-11. エンジニア向けの既存ツール（ADK、LangGraph、Dify、n8n、OpenAI Agents SDK など）との違いは

**答えの骨子**
- 既存のツールは「エージェントを**作る人**」の道具で、担当の分け方・権限・承認の条件・評価は作る人が書く。Makase は「作れない人」向けで、依頼文から担当と権限の分け方（読む担当は書けない、書く担当は外部を直接読まない）を Gemini が作り、Kernel の規則が検査する。利用者が触るのは、依頼を書く・○ を押す・[以後も許可]・[適用] の4つだけ。
- 2つ目の違いは、権限が**狭くなる方向にしか自動では変わらない**こと。広げると安全チェックからやり直しになり、通るまで確認に回る。
- 3つ目は、安全チェックが**利用者の画面にある**こと。レッドチーミングやシミュレーション試験は開発者の道具（[submission-text.md](submission-text.md) §3-2 の表）。
- 競うより上に乗れる関係：ADK を使わない理由は本ファイルの C-5 のとおり。
- 限界：いまの版で本物の書き込み先は Google カレンダーと GitHub、模擬の世界は仕入れの店舗だけ。好きなツールを自由につなぐ自由度は、既存のツールのほうが高い。Dify・n8n などは公開情報で細かく比べていない（§3-2 の表に入れた製品は出典つき）。
