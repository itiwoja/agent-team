## 2. リセット手順

審査用のトークンは、入れるたびに**新しいゲストのワークスペース**を作る（デモ用のデータ込み）。「最初からやり直す」は次のどれかで足りる。

1. **画面の [最初からやり直す] を使う（基本）**：メニューの中にある [最初からやり直す] を押す。今のワークスペースを削除予約にして、新しい用意した依頼（受信箱係 → 仕入れ係、固定のリハーサル結果、送る前の確認が1件）を作り直す。トークンの入れ直しはいらない。撮り直しのたびにこれで戻す。
   - 作成には上限がある：**同じ IP から1時間に5件まで、同時に50件まで**（BR-65）。撮り直しを繰り返すと当たるので、撮影の回数を決めて使う（下の3）。
   - 戻したあとは 1-2 の「撮影用の状態」（数字・送る前の確認1件・合格証がまだ出ていない）を確かめる。
   - 場面2で自分が頼んだ依頼（本物の Gemini が作った編成）も、やり直すと消えて新しいワークスペースになる。場面2・3b を撮り直すときもこの手順を使う。
   - 2026-10-05 に確認済み：[最初からやり直す] はメニューの中（合格証が出たあとはリハーサルの区画の下にも出る）。確認の文言は「最初からやり直しますか？」。押すと新しい用意した依頼のページに移り、数字・確認待ち1件・合格証なしの状態に戻る。
2. **代替：新しいワークスペースにする**：画面のやり直しが使えないとき（未デプロイ・不具合・上限）は、Cookie を消す（シークレットウィンドウを閉じて開き直す）→ 入口でトークンを入れ直す。前のワークスペースは7日で自動削除される。これも作成数の上限（下の3）の対象。
3. **作成数の上限に当たったとき**：同時に50件・同じ IP から1時間に5件まで（BR-65）。入口や [最初からやり直す] が「混み合っています」を返したら、時間をおくか別のネットワークから入る。既存のワークスペースは消えない。
4. **全体を壊れた状態から戻す**：直前の正常なリビジョンへ戻す。
   `gcloud run revisions list --service=app --region=asia-northeast1` → `gcloud run services update-traffic app --region=asia-northeast1 --to-revisions=<リビジョン名>=100`
   （`gateway`・`sim-world` も同様。ただし3サービスの版が揃っているコミットに戻す）。
5. **審査用のトークンを差し替える**（広まってしまったとき）：`gcloud secrets versions add guest-entry-token --data-file=-` で新しい版を足して再デプロイ。作成済みのゲストのワークスペースは消えない。**差し替えたら提出フォームの記載も直す**（提出後は修正できないので、提出前だけの操作）。

## 3. 失敗時の代替

| 症状 | 切り分け | 代替 |
|---|---|---|
| 入口で「準備中」と出る | 環境変数・Secret の不足（D-47）。`gcloud run services logs read app --region=asia-northeast1` に足りない名前が出る | 直るまで撮影を止める。直ったら 1-1 を最初から |
| 「エージェント生成中…」が終わらない・失敗する | Gemini の呼び出し失敗・クォータ。生成は30秒で打ち切り、60秒で `failed`（`timeout`）になる | 入力し直す。続くなら **用意した依頼のページ（入口の直後に開くもの）から撮り始める**（場面2の生成は録画済みの別テイクを編集でつなぐか、字幕で「生成中は5倍速」と出す。ただし Gemini が主役の場面なので、撮れたテイクを必ず1つは残す） |
| 自分の依頼の [リハーサルする]（場面3b）が遅い・失敗する | 同上。費用上限に当たっていないかも確認 | 待ち時間は字幕「5倍速」で詰める。失敗が続くなら別テイクを使う。固定の結果の場面4・5・7には影響しない |
| 用意した依頼の [本物の Gemini で走らせる] が遅い・失敗する | 同上。費用上限に当たっていないかも確認 | **固定の結果（事前に走らせた12件）を開いた状態**で、場面4・5・7を撮る。再試験だけ別テイクにする |
| 再試験や合格証が出ない | 締める提案の適用が失敗している可能性 | 画面の [最初からやり直す] で新しいワークスペースにしてやり直す（2. リセット手順の1） |
| [送らない] のあと「試験に入れました」の行が出ない | まず、[送らない] にしたのが**用意した依頼の確認**（判定「ルールにより、送る前に確認が必要です」）か確かめる。自分の依頼の確認（判定「リハーサルの合格証がないため…」。新しい画面では「安全チェックがまだなので、確認が必要です」）では出ない（2026-10-06 に確認）。それでも出なければ回帰の試験の配線（FR-066）。撮影前に試走で確かめておく | 場面8を「却下 → 監査ログに記録された」までに短くし、回帰の部分はナレーションで述べる前に実画面で動くことを確認してから戻す。動かなければ台本から該当の文を外す |
| 自動の再リハーサルが一瞬（1秒未満）で「合格」になる・「再リハーサル中」が見えない | メニューの「今日の残り $x」が少ない。ゲストの1日（D-106 で $4。それより前に作ったワークスペースは $1・$2）を使い切ると、状況が予算切れ（`budget_exceeded:budget.per_day_usd`）で Kernel に止められる（2026-10-06 は合格になる不具合があった。f7743f1 のあとは `aborted(budget)`・合格証なし） | [最初からやり直す] で新しいワークスペース（今日の残り $4.00）にして、場面8を撮り直す。場面3b の自分の依頼のリハーサルは、場面8 と同じワークスペースで走らせない |
| 画面が崩れる・古い見た目 | `apps/web` の見た目の更新（D-100）が未デプロイ | デプロイ版が最新か確認（1-1）。最新でなければ再デプロイしてから撮る |
| 429 `GUEST_LIMIT_REACHED` | 作成数の上限（BR-65） | 時間をおく。IP を変える |
| Gemini の費用が急増した | 予算アラートの通知 | `sa-app` から `roles/aiplatform.user` を外す（画面・承認・Kill Switch は動く。`infra/README.md` §緊急時）。撮影は固定の結果で行う |
| 公開デプロイ全体が動かない | Cloud Run・Cloud SQL・NAT のどこか | 撮影はローカルで行い（`README.md` §ローカルでの起動）、動画に「ローカル環境」と字幕を入れる。**提出用 URL は必ず直す** |

## 5. 提出後の運用（10/16〜12/1）

ルールは「12/1 まで、提出時点のデフォルトブランチ・稼働環境を維持する」。`main` に push するとデプロイが動いて稼働環境が変わるので、提出後は `main` を動かさない。費用は `docs/submission/measurements/cost-per-run.md` の[12/1 まで動かし続ける費用の見込み](measurements/cost-per-run.md#121-まで動かし続ける費用の見込み)を参照する。

順番は **最後の変更のマージ → デプロイの確認（0）→ タグ（5-1）→ 保護（5-3）**。保護を先に入れると、最後のマージが止まる。

0. 最後の変更を `main` にマージしたら、`deploy.yml` の成功とスモークテストの通過、`/api/health` の `commit`（`apps/app/src/app.ts` が `deps.env.commitSha` を返す）が `main` の HEAD と一致することを確かめてから、タグを打つ。締切の数時間前までにマージを終える。

### 5-1. 提出時点のコミットを控える（10/15、提出の直前）

1. `git fetch origin && git rev-parse origin/main` で `main` の HEAD の SHA を控える。提出フォームのリポジトリの記載、`/api/health` の `commit`（1-1 の最初の項目）と同じであることを確かめる。
2. その SHA にタグを打って push する：`git tag -a submission-2026-10-15 <SHA> -m "提出時点のコミット"` → `git push origin submission-2026-10-15`。
   - タグの push では `deploy.yml` も `ci.yml` も動かない（`deploy.yml` は `on.push.branches: [main]`、`ci.yml` は `branches-ignore: [main]` の指定だけでタグの指定がない。2つのファイルを読んで確認）。
3. SHA とタグ名をこのファイルの外（提出フォームの控え、手元のメモ）にも残す。あとで「提出時点から `main` が動いていない」ことを `git rev-parse origin/main` とタグで示せるようにする。

### 5-2. `main` には push・マージしない。継続開発は別ブランチ

- `deploy.yml` は `on.push.branches: [main]` だけで動く。つまり `main` への push（PR のマージも push になる）が、イメージのビルド → マイグレーション → Cloud Run の `app`・`gateway`・`sim-world` の入れ替えまで走らせる。
- 別ブランチへの push と PR は、`ci.yml`（型・テスト・依存の境界・zizmor・gitleaks）だけが動き、`deploy.yml` は動かない。WIF のプロバイダーも「このリポジトリの `main` への push」だけを通すので、PR や別ブランチからは GCP に入れない（`deploy.yml` 冒頭のコメント）。
- 継続開発は `claude/…` などの別ブランチで進めてよい。ただし 12/1 までは `main` にマージしない。PR は開いたままにするか、下書き（Draft）にしておく。
- GitHub の既定のブランチ（デフォルトブランチ）の設定も変えない（提出時点のデフォルトブランチのまま）。

### 5-3. GitHub のブランチ保護を入れる（10/15、最後のマージ・デプロイ確認・タグのあと）

誤って `main` に push・マージしないように、設定で止める。GitHub のリポジトリの画面で行う。

1. リポジトリの [Settings] → [Rules] → [Rulesets] → [New ruleset] → [New branch ruleset] を開く。
2. Ruleset Name に `freeze-main-until-1201` など分かる名前を入れ、Enforcement status を **Active** にする。
3. Bypass list は**空のまま**にする（管理者・自分も例外にしない）。
4. Target branches は [Add target] → [Include default branch]（`main`）。
5. Branch rules で次を入れる：**Restrict updates**（push と更新を止める）・**Restrict deletions**・**Block force pushes**・**Require a pull request before merging**。
6. [Create] で保存する。
7. 確かめる：`gh api repos/<owner>/<repo>/rules/branches/main` に `update`・`deletion`・`non_fast_forward`・`pull_request` の4つが出ること、PR の画面で [Merge] が押せないことを見る。`main` への試しの push はしない（通るとデプロイが走るため）。
8. 旧式の [Settings] → [Branches] → [Add branch protection rule] でも近いことはできるが、管理者が例外になる設定（[Do not allow bypassing the above settings] を入れていない場合）では止まらないので、上の Ruleset を使う。

保護を外すときは、Ruleset の Enforcement status を Disabled にする。外す操作自体が提出状態を変える判断なので、5-4 の手順に従う。

### 5-4. 緊急の修正が必要になったときの判断

提出状態の維持が最優先。次の順で考える。

1. **ルールの再確認**：ハッカソンの規約の「12/1 まで提出時点のデフォルトブランチ・稼働環境を維持」の文面と、修正が許されるか（バグ修正は可か）を、事務局の案内で確かめる。分からなければ事務局に問い合わせる。確認が取れるまで `main` は動かさない。
2. **コードを変えずに止血する**：まず `main` を触らない手段で対処する。
   - 直前の正常なリビジョンに戻す（2. リセット手順の4。`main` は動かない）。
   - Gemini の費用が急増したら、`sa-app` から `roles/aiplatform.user` を外す（3. 失敗時の代替の表。画面・承認・Kill Switch は動く）。
   - 審査用のトークンが広まった場合の差し替えは、提出後は提出フォームを直せないので、基本は行わない（2 の5）。
3. **それでも `main` の変更が要る場合**：事務局の許可を得てから、保護を外して修正を入れ、同じ手順でタグ（例 `submission-2026-10-15-fix1`）と保護を戻す。修正の内容・日時・許可をどこかに残す。許可が取れないときは `main` を変えず、継続開発のブランチだけに入れる。
4. 軽微な見た目や文言の修正は、12/1 の最終ピッチまで待つ。
