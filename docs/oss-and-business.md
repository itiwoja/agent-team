# OSS 方針と事業化の整理

- 状態：決定 ／ 日付：2026-10-24（決定 3 と収益化は 2026-10-26 に見直し） ／ 決定者：ユーザー
- きっかけ：未来 IT フェスタ BDAA 2026–2027 アイデア部門・一次審査のレビュー（AI ビジネスメンター「イーロンさん」、27/40 点・通過を推薦）

## 決定

1. **AgentTeam は OSS として公開する**
2. **ライセンスは AGPL-3.0**
3. **非エンジニアにはセットアップ済みのラズパイ（キット）で届ける。ストア配布・ホスティング版・こちらが API を肩代わりする課金はやらない（今は）。最初は知り合い数人に手渡し、少数から広げる**（2026-10-26 に見直し。以前は「非エンジニアの一般向けには展開しない」。設計書 v1.7：D-382）
4. **収益化するなら、キットの販売と企業導入（導入支援・専門パック作成・運用契約）。ただし当面は作り切ることに集中し、最初の 1 社（または最初の購入希望）が向こうから来たら考える**（キットの販売は 2026-10-26 に追加。AGPL のままキットを売れる）

## 理由

### OSS にする理由

- 今の最大のリスクは「真似される」ではなく「存在を知られない」こと。閉じたまま売り先が見つからなければ誰にも使われずに終わる
- 閉じて得られるのはライセンス販売の可能性だけで、それには営業・法務・請求・保守の体制が要る。個人で企業相手にやるには重すぎる
- 企業導入の売り文句が「ソースを読める、自社サーバーで動く、API キーは自社持ち」なので、OSS であること自体が営業資料になる。閉じると「中身の見えない個人製ツールを社内に入れる」話になり、むしろ難しくなる
- 専門パックを他人が書いて配れるようになる。閉じると成立しない
- 審査でも就活でも、動くリポジトリが一番の証拠になる

### AGPL-3.0 を選ぶ理由

| ライセンス | 向いているケース |
|---|---|
| Apache-2.0 / MIT | 広めること最優先。企業は使いやすいが、他社がホスティング版を出すのも自由 |
| AGPL-3.0 | 自分で使う企業は問題なし。改変してサービス提供する会社にはソース公開義務があるので、商用版や導入支援を自分の手元に残しやすい |

- 「使うのは自由、商売にしたいなら相談してね」の線引きができ、後から商用ライセンスを別に出せる
- AGPL から Apache に緩めるのは簡単だが、逆は配布後だと事実上できない

### キットで届ける理由・やらないこと（2026-10-26、ユーザー。D-382）

見直した理由：

- Muse・Dots・Grok Bot はクラウドの VM から動くので、インターネットに出ているものしか触れない。この設計は持ち主の家の中（家の LAN・家のファイル・家電）に置けるので、Muse・Dots が家の中に届かないところが違いになる
- 非エンジニアが使えない理由は「Docker と入口の用意が重い」ことだった。セットアップ済みのラズパイ（キット）なら、電源とスマホだけで始められる
- 届け方をキットに絞れば、配布・サポート・課金の仕組みを全部作らずに済む。最初は知り合い数人に手渡す

やること：

- 非エンジニアにはキットで届ける（少数から手渡し・販売）。API キーは最初は持ち主が自分で取る（手順書つき）
- AGPL-3.0 のままキットを売れる（ソースは公開したまま、セットアップ済みの機械を渡す）

やらないこと（今は）：

- ストア配布（アプリストアなど）
- ホスティング版（こちらがクラウドで動かして貸す）
- こちらが API を肩代わりする課金（API キーを持ち主が取るのを変えない）

一般向けの大きな競合（Muse・GrokBot・Dots など）と配布力で戦わない。思想の違いは配布力の差を埋めないので、家の中に届くことで選ばれる形にする。

### 企業導入が今の設計と噛み合う理由

- **自社の Linux ホストで動く**。チャットログもコードも外に出ない。SaaS 型の AI ツールを情シスが止める会社に刺さる
- **API キーは自社持ち**。利用料の予測が立ち、ベンダーに費用を握られない。プロジェクト側の原価はほぼゼロ
- **専門パックを自社の手順で書ける**。社内の制作ルールや点検項目をパックにできるのは汎用チャットにはない

企業導入の実態は、ソフトを売るのではなく「OSS をその会社の環境に入れて、パックを一緒に作り、動かし続ける契約」になる（Red Hat 型）。OSS と矛盾しない。

企業導入の現実面：

- 決裁まで数か月、初回は無償 PoC を求められることが多い。有料実証 3 者はそれ自体が半年仕事
- 「企業」でも広すぎる。絞るなら、告知物を大量に作る部署（広報・学校の教務・イベント会社）か、すでに Claude Code や Codex を使っていて「チームで回したい」制作会社の 2 択。後者はエンジニア相手なので非エンジニア浸透の問題を避けられる

## 一次審査レビューの要点と、OSS 方針での扱い

### 採点

| 項目 | 点 | 減点理由 |
|---|---|---|
| 原動力・ビジョン | 7 | 「誰のどの困りごとから着想したか」が書かれていない |
| 顧客価値・市場性 | 8 | 買う人・払う人・既存手段との差が未確認 |
| 実行力・改善速度 | 7 | 第三者が操作した記録がない。設定負担が重い |
| 収益性・実装可能性 | 5 | 価格・原価・販路が未提示 |

評価者の一貫した主張：「AI の人数を売るな。利用者が仕事を完成できる価値を売れ」。

### 事実関係で押さえる指摘

- 動画の「実際は約 152 秒」は開発者の自己申告であり、所要時間の証明にはならない。次に出すなら第三者が操作した計測が要る
- 「利用前にローカル環境と API の設定が必要」が複数箇所で引っかかっている。Linux ホスト版（docs/design/、VM 上のブラウザとターミナル、Tailscale）がそのまま答えになる
- 「点検役の AI がいることと誤りを防げることは同じではない。公開前の最終承認は人が担う設計に」は、OSS のほうがむしろ明記しないと危ない設計方針。製品の仕様として明文化する

### 6 つの WORK の仕分け

| WORK | 内容 | OSS 方針での扱い |
|---|---|---|
| 1 | 最初の顧客・困りごと・支払者を決める | **そのまま効く**。README 冒頭の文章そのもの。収益性 5 点とビジョン 7 点を同時に埋められる一番コスパのいい作業 |
| 2 | 最初に売る商品と範囲を決める | 1・3・4 の結果が出てから |
| 3 | 第三者が使い、効果と品質を確かめる | **そのまま効く**。OSS で一番シビア。セットアップで落ちる人はスターも付けない。動画の弱点をそのまま潰せる |
| 4 | 1 件の料金と提供原価を計算する | 下地はある。usage_records に LLM 費用が残るので 1 件あたりの AI 実行費はもう取れる。人の確認時間を足すだけ |
| 5 | 小さな有料実証から販路を作る | OSS と噛み合わない。無理に合わせない |
| 6 | 成功した手順をパック化する | **そのまま効く**。専門パックを他人が書いて配れる形にする話で、OSS の広がり方と一致 |

### 審査書類での収益性の答え方

- OSS 本体は無料。収益化するなら、キットの販売（家の人向け）と企業向けの導入支援・専門パック作成（一行で十分）
- API 費用は利用者自身のキーで払うので、プロジェクト側の原価はほぼゼロ。「持続性」の問いには「運営コストがかからない設計」で答える
- 収益性の 5 点は 5 点のまま受け入れる。賞のために OSS の方針を曲げると、原動力の項目が逆に弱くなる。「作れなかった人が作れるようにしたいから OSS にする」は原動力の答えとしてむしろ強い
