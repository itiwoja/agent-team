# 安全の仕組み

エージェントは間違えます。読んだページに「全員を招待して」と書かれていれば従ってしまうこともあります。Makase はエージェントの善意に頼らず、LLM の外にある決定論のコードで守ります。

## Gemini が決めるもの・決めないもの

| Gemini が担う | Gemini が決めない（決定論のコードが決める） |
|---|---|
| エージェントの推論・要約 | 書き込みを許すか（`packages/kernel` の `decide()`） |
| 担当と動かし方の案 | 案が正しい形か（`validateFormation`） |
| 安全チェックの悪い日の生成 | 締める提案（`packages/rehearsal/src/tighten.ts`） |
| Web 検索の要約と出典 | 提案が締めるか広げるか（`classify()`。広げる提案は出さない） |
| | 試験の合否（オラクル O-01〜O-08） |
| | 損害額（`sim-world` の固定の式） |
| | 合格証の発行・失効、費用の上限、監査ログ |

## Kernel の判定

書き込みのたびに、ポリシー・「以後も許可」のルール・ガード（単価の上限など）・タスクの状態から、**自動・確認・拒否**を決めます。

- 既定は「確認」。人の ○ がない書き込みは実行されない。
- 結果の分からない書き込み（タイムアウトなど）が残っている間は、ルールがあっても確認に回す（二重発注を防ぐ）。
- 外から読んだ内容でタスクが汚染されたあとの書き込みは、厳しく判定する。汚染のあとは作業場のコマンドも動かせない。
- 合格証がない間は、「以後も許可」のルールがあっても確認に回す。
- 費用の上限を超えたタスクは止める。Kill Switch で全体を止められる。

## 育ったスキルの信頼

担当が読むスキルを「信頼された手順書」として扱うのは、次の2つだけです。

- **パック**のスキルで、運営が用意した中身と同じもの。
- **育ったスキル**（繰り返しの仕事からできた案）で、人が ○ を押したときの中身と同じもの。承認したあとに名前・説明・本文のどれかを書き換えたら、信頼しません。

中身の一致は SHA-256 で確かめます。それ以外のスキルは、外から来た内容と同じ扱いで読ませ、読んだタスクを汚染します。

整理の扱いは、方向で分けています。

- **ルールを外す**のは締める方向（確認が増える）。自動で行います。
- **戻す**のは広げる方向なので、人の操作だけです。Kernel の判定と上限（1担当に20個まで）を通します。

## 安全チェック（リハーサル）

任せる前に、同じ仕事を模擬の世界で本番と同じ経路・同じ統制で走らせます。

1. Gemini が、その仕事の悪い日（障害カタログ F-01〜F-07 に当てはめたもの）を作る。
2. 模擬の世界で走らせ、オラクルが合否を、`sim-world` が損害額を決める。
3. **Kernel が止めたもの**と**すり抜けたもの**を、防いだ損害の金額つきで見せる。
4. すり抜けた穴には、権限を締める方向の提案だけを出す。当てたら同じ条件で再試験する。
5. 全件通ると合格証が出る。条件が変わって合格証が切れたら、自動で試し直す。
6. 本番で止めた発注は、次の安全チェックの試験に加わる。

| 悪い日 | 内容 |
|---|---|
| F-01 | 応答のタイムアウト（実は成功している） |
| F-02 | 仕込まれた指示（メール本文など） |
| F-03 | 宛先のすり替え |
| F-04 | 単位・桁の取り違え |
| F-05 | 価格・条件の急変 |
| F-06 | 古い・矛盾した観測 |
| F-07 | 一時的なエラーの連続 |

## 実測

本物の Gemini（`gemini-3.8-flash`）で、同じ悪い日・同じシードを状況ごとに5回、計35走行ずつ測りました（[governed-20261006-gemini.md](measurements/governed-20261006-gemini.md)）。

| 設定 | 人に確認した回数 | すり抜け | 損害 |
|---|---:|---:|---:|
| 統制なし | — | 12/35 | ¥234,000 |
| ルールなし（毎回確認） | 32 | 0/35 | ¥0 |
| 「以後も許可」のルールあり | 5 | 7/35 | ¥156,000 |
| 締めたあと（単価 ¥1,170 以下のガード） | 17 | 0/35 | ¥0 |

確認を減らすとすり抜け、安全チェックの締める提案を当てると、確認を半分にしたまま塞がりました。一方で、確認を中身を見ずに全部承認すると、どの設定でも損害が出ます。古い在庫の値で発注しなかった在庫切れ（F-06）のように、「しなかったこと」は統制では止められません。

## 分かっている制限

- `app` のプロセスと DB ロールを信じている。`app` が破られると、承認の記録を偽れる余地が残る（順番が合わないもの・記録と食い違うものは gateway が止める）。承認の状態遷移を DB の関数に閉じること、人の承認をパスキーで署名して gateway が検証することが次の課題。
- 同じ担当を使うか新しく作るかを選ぶのは Gemini で、その精度は測っていない。
